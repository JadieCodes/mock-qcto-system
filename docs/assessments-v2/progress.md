#### EISA Registration + Confirmation assumptions made

- **The assessment centre defaults to the registering SDP.** The old build's registration screen never captured a separate "assessment centre" field, so `eisa-confirmation/api.ts` `generateConfirmation()` groups the consolidated learner list by `registration.sdpName`. The QP's "confirm the assessment centres" step confirms learner counts per that same grouping rather than renaming/splitting centres. Revisit if QCTO says assessment centres are a distinct concept from SDPs.
- **"Dates within the sitting" (CR-043) is read as on/after the sitting date.** `eisa-confirmation/api.ts` `confirmDetails()` blocks a marking date before the sitting date and a moderation date before the marking date — the register doesn't give an exact window, and marking/moderation logically can't happen before the exam is written.
- **"Active or concurrent EISA registration" (CR-040) means the learner appears on any other registration record, in any stage** (`sdp-submission`, `ad-review`, or `registered`), not only a fully `registered` one — a learner mid-registration elsewhere is still "concurrent".
- **PM-08's Non-Trades hand-off is simulated as an audit entry plus a QP notification**, not a new screen or a QA-domain inbox — the Quality Assurance domain has no role in this build's `Role` union to notify directly, and the register doesn't specify what "sharing the SDP list" looks like on QA's side.
- **The Assistant Director both processes registration and generates the EISA Confirmation** (`eisa-confirmation/config.ts` → `CONFIRMATION_GENERATOR_ROLE`) — the register names only "QCTO officials" for Confirmation, so it follows the same role that already owns Registration immediately before it, same pattern as the EISA Calendar's `CALENDAR_REVIEWER_ROLE` assumption.
- **CR-038's SOR flag is a per-learner flag inside `ad-review`, not a whole-record send-back to `sdp-submission`.** The register says the official "can flag an individual SOR... which notifies the SDP to correct and resubmit" — read literally as scoped to that one learner, so the registration itself never leaves Assistant Director review and the SDP only gets a narrow "re-upload this one SOR" action.
- **One registration can hold learners with mixed RPL/ARPL flags; the automatic monitoring-item trigger fires once per registration**, listing every flagged learner on it, rather than creating one monitoring item per learner. The register says the indicator "automatically creates a monitoring item" (singular) without specifying granularity.
- **A QP visiting EISA Registration, and an SDP visiting EISA Confirmation, see the same list read-only.** No CR restricts either direction (unlike CR-018's explicit SDP block on Instrument Validation), so both nav items stay visible to both external roles; only the role that the CR names for each action (SDP for registration, QP for confirmation) sees the action buttons.

## Assumptions made

- The v2 role switcher is fully self-contained (`shared/ui/RoleContext.tsx`), independent of the app-wide `AppContext.currentRole`. The old build's role selector mutates one global role shared by every domain; v2's hard rule 3 forbids importing `AppContext` anyway, so this was a forced — and, since it stops a v2 role switch from leaking into other open domains, desirable — design choice. Confirmed with the developer before Phase 0B build began.
- React Query cache is never the source of truth for workflow/domain state — `mock/api` (memory + localStorage) always is. The query client is scoped to `index.tsx` only, instantiated once at module scope, and never touches `App.tsx`'s client (which root `CLAUDE.md` already flags as recreated-every-render — a pre-existing issue outside this module's remit to fix).
- `/assessments-v2` is reachable directly by URL with no department-login gate (matching `06-swap-plan.md`), so a persistent "Demo — mock data only" banner is shown in the v2 header at all times.
- **SAQA registry check lives in `mock/api/saqaRegistry.ts`, not `mock/integrations/`.** The module `CLAUDE.md`'s "Data" section explicitly lists "SAQA registry" as cross-domain data simulated in `mock/api`, while `mock/integrations/` is reserved for the backend-only CRs with no screen (CR-001, 002, 009, 010, 020, 022, 037, 039). Since the gate check has a screen (the New Application form), it follows the `mock/api` convention. There is no real SAQA API, so the QP simulates the outcome with "Registered"/"Not Registered" buttons, same UX as the old build.
- **"A different actor" means a different role, not a different individual.** This build has no per-user login — only a role switcher (`RoleContext`) — so `requiresDifferentActor` (CR-053) compares the role label stored as `submittedBy` against the current role's label. Within a single role this is indistinguishable from a real per-user check because the workflow already prevents the same role from acting twice in a row (the stage moves on); it only becomes a real gap if QCTO later wants to stop e.g. two different ASDs approving each other's work, which needs real individual logins.
- **The external dashboard shows every application, not just one QP's.** "My QSA Addendum applications" has no QP identity to filter by — the QP name on an application is a free-text form field, not a login. Revisit if/when the app gains real QP accounts.
- **IAC decline vs. remediation are different terminal directions.** A decline moves straight to the outcome-letter flow (the CEO signs a letter saying "Declined" — confirming the process was followed, per CR-008's intent). "Send for remediation" instead loops back to the ASD so the application can be reworked and re-evaluated. Process-flow.md's wording ("a decline sends it back for remediation") reads as if these are the same thing, but CR-016 lists them as separate actions ("decline or send for remediation") — built as two distinct buttons so both are directly testable.
- **Approval letter signer defaults to the Deputy Director.** Open question (CR-007/CR-008 follow-up) answered with the simplest reading — one constant, `modules/qsa-addendum/config.ts` → `APPROVAL_LETTER_SIGNER_ROLE`, to change if QCTO names someone else.
- **Approved EISA sittings per year is captured on the QSA Addendum evaluation.** Open question (CR-030) answered with the simplest reading — a field on the ASD's evaluation report (`evaluationReport.approvedEisaSittingsPerYear`), not a separate screen. Move it if QCTO confirms a different home for this value.
- **IAC remediation goes to the ASD, who can then return it to the QP.** "Remediation goes back down the chain" (CR-016) is built as IAC → `asd-evaluation` directly — the same stage the ASD already works from, which still has its own "Return to QP for corrections" action if the ASD decides the QP needs to make changes. There is no separate remediation-only stage.

- **No specific role is named for the EISA Calendar, so the ASD reviews/publishes/postpones/cancels.** The register and process-flow.md both say only "QCTO officials" (CR-027/CR-032). Implemented as `modules/eisa-calendar/config.ts` → `CALENDAR_REVIEWER_ROLE` (`'ASD'`) and added to the ASD's teams in `config/roles.ts` (`eisa-calendar`, alongside the ASD's existing `qsa-evaluation`/`instrument-validation` teams) — one constant to change if QCTO names a different role.
- **The minimum lead time is expressed in working days (21), using the same shared helper Phase 6 needs for its 21-working-day results SLA.** Neither the figure nor the unit (calendar vs working days) is in the register (CR-032 open question). `config/holidays.ts` → `MIN_LEAD_TIME_WORKING_DAYS`.
- **The SA public holiday list is a best-effort 2026–2027 list, not from a QCTO-confirmed source.** `config/holidays.ts` → `SA_PUBLIC_HOLIDAYS`. Confirm the real source (CR-032 open question) before relying on it past the demo.
- **"Approve" and "publish" are two separate QCTO actions, not one combined step.** CR-028's prose reads sequentially ("QCTO validates and approves them, then they are published"), and the developer's own requested click-through script lists them as three separate steps (approve / reject with reason / publish) — built that way in `BATCH_WORKFLOW` (`qcto-review → approved → published`).
- **The automatic date checks (CR-032) hard-block a QP's proposal, but only warn (non-blocking) when QCTO adds or edits a sitting directly.** CR-027 gives QCTO unrestricted add/edit/delete ("at any time"), while CR-032's "reject dates automatically" reads as being about the QP-facing submission path. QCTO can override; `internal/AddEditSittingDialog.tsx` shows the same `checkSittingDate` result as a dismissible warning instead of a block.
- **Postponing a sitting does not auto-create a replacement date.** The register doesn't ask for this, and "stages are not auto-triggered" is a running theme in this build (CR-024, CR-044) — QCTO adds a new date separately (CR-027) if the sitting needs to be rescheduled.
- **The external "EISA Calendar" screens show every QP's/SDP's submissions and sittings, not filtered to "my own".** Same reason as the QSA Addendum module's existing assumption: there is no QP/SDP login, only the role switcher, so there is no identity to filter by.
- **Cancellation/postponement notifications go to both the SDP (explicitly required by CR-034) and the QP** (their qualification's sitting changed) — `api.ts` `performSittingLifecycleAction` calls `addNotification` twice, once per recipient role.
- **SDPs see only `published`, `postponed` and `cancelled` sittings** (`external/SdpCalendarView.tsx`) — the earlier internal-only stages (`proposed`, `approved`, `rejected`) are a QP ↔ QCTO matter, mirroring CR-018's "SDPs never see EISA Instrument Validation".
- **The "Quality Assurance module's scheduling methodology" CR-017 says to reuse could not be located as a distinct propose/accept/counter-propose feature anywhere under `src/pages/QA/`.** That folder's site-visit code (`subtabs/SiteVisitManagement.tsx`) is a one-sided evaluation tool with no joint negotiation. The closest shape that does exist is `src/pages/accreditation/SiteVisitManagement.tsx`'s one-sided schedule → send → applicant-accept/reschedule-request chain (a different domain, read-only reference per the module's hard rule 3). `modules/instrument-validation/workflow.ts`'s `SCHEDULING_WORKFLOW` is a fresh two-party propose → accept/counter-propose state machine built in the same shape (a `WorkflowDefinition` through the shared engine) rather than a literal port of either. Flag to the developer: confirm whether a different QA scheduling feature exists that this should have matched instead.
- **One instrument validation per QSA Addendum.** The register doesn't say whether a qualification can have more than one validation record (e.g. for a second instrument). `api.ts` `startValidation()` blocks starting a second one for the same addendum; `listEligibleQsaAddenda()` drops any addendum that already has one. Revisit if QCTO confirms multiple instruments per qualification are normal.
- **"QSA agenda" (CR-025) is read as the QSA Addendum queue** — the same applications already listed on the QSA Addendum module's own internal dashboard — shown alongside instrument validation status in one combined view (`internal/StatusDashboard.tsx`), not as a separate, differently-shaped screen. Filters: free-text search (qualification/QP/stage), type, and a submitted/created date range.
- **The QSA Addendum doesn't capture a QP postal address or a named contact person**, so two of CR-021's pre-filled fields (Address of QP, Contact Person/Number) always start as a placeholder needing Recapture — there is nowhere upstream to pull a real value from yet. `modules/instrument-validation/config.ts` → `PREFILL_NOT_CAPTURED_PLACEHOLDER`. Raise with QCTO whether these belong on the QSA Addendum submission form instead.
- **"Not approved" is treated as "changes required"; "Approved" and "Approved with conditions" are both treated as not requiring changes.** The old build had a separate "Changes Required" checkbox alongside the 3-option outcome decision; CR-023 only says "if changes are required the QP fixes and resubmits" without naming a separate flag, so the simpler reading — Not Approved always loops back, the other two always mark the instrument Validated — was built instead of adding an extra field the register never asked for.
- **A resubmission cycle gets a brand-new checklist and pre-filled fields, not the previous cycle's answers carried forward.** CR-011's mandatory-comment checklist is meant to be a genuine re-check of the resubmitted instrument, not a resave of stale answers; `outcomeHistory` keeps every past cycle's decision and notes so nothing is lost.
